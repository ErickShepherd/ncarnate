CI dependencies
===============

Runtime packages
----------------

ncarnate uses five direct runtime dependencies: netCDF4 for netCDF I/O,
NumPy for arrays, pyhdf for HDF4 access, pyproj for coordinate transformations,
and tqdm for CLI progress. Each has active uses in the package. Internet
Archive is not a runtime dependency and ncarnate does not contact it when
converting files. The Python standard library handles validation-data downloads;
no new runtime package is needed for retrying them.

The dependency floors in ``pyproject.toml`` match the conda-forge recipe.
Conda-forge's October 2026 rerender uses Python 3.11 or newer; PyPI supports
Python 3.10 or newer. CI tests current resolved dependencies on supported
platforms, rather than every combination of minimum dependency versions.
This review does not establish that every transitive dependency is free of
security advisories. Runtime version changes should receive their own
compatibility testing rather than being bundled into a download-retry fix.

Full-size validation data
-------------------------

Ordinary tests use committed, trimmed fixtures and require no external data
downloads. The separate full-granule workflow needs five original satellite
files and one independent HDF Group conversion. Their exact checksums are
recorded in ``tests/fixtures/corpus.json``. Keeping the independent conversion
matters: an output generated by ncarnate itself would not provide an independent
reference for the comparison.

Four files currently come from Internet Archive snapshots of the old HDF
Group sample server. Two come from the STAREPandas GitHub repository. The
checksums protect their identity even if a remote URL changes, but neither
host is controlled by this project. An outage can prevent a fresh validation
run without indicating a conversion bug.

On October 8, 2026, probes of the four original HTTPS URLs on
``gamma.hdfgroup.org`` ended without a response. The current
`HDF Group GrADS examples <https://www.hdfeos.org/software/grads.php>`_
link to OneDrive instead; the RainGrid share returned HTTP 503 in a direct
probe. These observations do not establish permanent unavailability, but no
replacement has yet been verified against the pinned checksums. The existing
sources remain in place until a replacement's exact bytes are verified.

Immediate safeguards
--------------------

* Up to three attempts per URL for timeouts, temporary DNS/connection failures, incomplete
  transfers, and HTTP 408, 429, 500, 502, 503 and 504, with 2- and 4-second
  pauses. Permanent errors and checksum failures move to the next listed
  mirror without retrying the same URL.
* A 30-second socket timeout, a 120-second transfer budget checked between
  reads, and a 512 MiB size cap per attempt. A blocked read can extend the
  transfer budget by at most its socket timeout. The workflow also has a
  30-minute job limit.
* Temporary files are removed after every attempt. Only a complete download
  matching the pinned checksum can become a corpus file.
* A GitHub Actions cache keyed by the manifest avoids repeated downloads.
  Every restored file is hashed again. Invalid cached files fail validation;
  investigate and delete the affected cache before retrying. No broad cache
  restore key can silently select a different manifest.
* Cache saving happens only after the entire corpus verifies. Download errors
  appear on stderr, while stdout remains a machine-readable JSON report.
  Missing data and skipped tests still fail the job.

Durable replacement
-------------------

The recommended next step is a versioned validation-data release in a
project-controlled repository or durable object store. Preserve the six
original files unchanged, their checksums, source attribution, and the
independent reference's provenance. Confirm redistribution terms before
publishing that mirror. Add verified mirror URLs first in the manifest and
retain the original/archived URLs as fallback evidence. Do not substitute a
new product revision or regenerate the independent reference to make CI pass.

GitHub caches can be evicted and PR caches have branch scope, so caching is
an optimization rather than durable storage. Successful runs on ``main``
populate a cache subsequent pull requests can restore. A cold run still
depends on the external sources until the controlled mirror exists.
